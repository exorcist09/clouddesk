2. Product overview
Build a Smart Customer Support Agent for a fictional B2B SaaS company named CloudDesk.
CloudDesk receives support tickets about billing, technical problems, and account management. The system must automate routine support requests while escalating sensitive, risky, or uncertain requests to a human manager.
The application consists of:
A Next.js with bun frontend for ticket management and human review.
A Python + FastAPI backend for REST APIs and business logic.
A LangGraph workflow for classification, specialist routing, tool calling, escalation, and human review.
PostgreSQL with pgvector for application data, vector search, and persistent workflow state.
Docker Compose to run the entire application locally.
The primary objective is correctness, reliability, and a working end-to-end flow—not visual polish.

4. Core workflow
Implement the following logical flow using LangGraph:
Receive ticket → classify → evaluate confidence → route to specialist → retrieve information using tools → draft reply → apply escalation rules → auto-resolve or pause for human review → finalize.
Each stage must have a clear responsibility.
Ticket input
Accept:
Customer name or ID.
Customer email.
Subject line.
Message body.
Persist the ticket before beginning processing so it remains available if the workflow fails.
Classification
Classify each ticket into exactly one of these domains:
BILLING
TECHNICAL_SUPPORT
ACCOUNT_MANAGEMENT
Return a validated structured result containing the domain, confidence score between 0 and 1, and a brief explanation.
Use configurable confidence thresholds. Low-confidence tickets must be escalated directly to human review rather than routed for automatic resolution.
Do not rely exclusively on keyword matching for classification. Use an LLM with structured output, followed by deterministic validation and escalation rules.
Specialist routing
Route the ticket to the appropriate specialist based on the validated classification.
Each specialist must use tools to retrieve relevant information. The model must not invent customer records, payment history, subscription details, help articles, or account settings.
Structured draft response
Generate a structured draft containing:
Reply text.
Brief summary of the issue.
Information or sources used.
Whether the ticket requires escalation.
Escalation reason, when applicable.
Validate the output before storing or using it.

5. Specialist domains and business rules
A. Billing specialist
Responsibilities:
Payments.
Invoices.
Charges.
Subscription plans.
Refund-related questions.
Billing history.
Required tools:
get_customer_billing_history(customer_id)
get_current_subscription(customer_id)
Tools must query PostgreSQL and return actual matching mock records.
Escalation rules:
Refund requests.
Billing disputes.
Amounts above ₹5,000.
A ticket describing a duplicate charge is a billing dispute and must be escalated, including the supplied example involving two charges of ₹2,999 each.
Do not automatically issue refunds or perform financial transactions.
B. Technical support specialist
Responsibilities:
Bugs and errors.
How-to questions.
Feature questions.
Known technical issues.
Outage information.
Required tools:
search_knowledge_base(query)
get_known_bugs(query)
get_outage_status(service)
Implement relevant retrieval using pgvector. Known bugs and outage status should come from seeded records or appropriate database queries.
Escalation rules:
No relevant help article found.
Data-loss concerns.
Security concerns.
A known issue with a relevant workaround can receive an automatic draft and be resolved if no other escalation rule applies.
C. Account management specialist
Responsibilities:
Login issues.
Password-reset guidance.
Team management.
Account questions.
Account details.
Required tools:
get_account_details(customer_id)
search_knowledge_base(query)
Account details must include, where available:
Customer email.
Subscription plan.
Two-factor authentication status.
Team size.
Escalation rules:
Account deletion.
Ownership transfer.
Unauthorized access.
Never perform account deletion, ownership transfers, or sensitive account changes automatically.
Escalation precedence
Implement deterministic escalation checks after classification and specialist processing.
If a ticket matches a mandatory escalation rule, it must not be auto-resolved even when the model is highly confident.
If a ticket has low classification confidence, escalate before invoking a specialist.
The backend—not the LLM alone—must enforce these safety rules.

6. Human review and resumable workflow
Human review is a core feature.
When escalation is required:
Save the classification, specialist results where available, draft, and escalation reason.
Set the ticket to PENDING_REVIEW.
Persist the LangGraph execution state and interrupt the workflow.
Display the ticket in the frontend review queue.
Allow a manager to approve, edit, or reject the draft.
Persist the decision and reviewer information.
Resume the paused graph using the persisted checkpoint.
Apply the decision and update the ticket's final status and response.
Review decisions
Approve: Accept the draft and finalize the ticket according to the workflow.
Edit: Save the manager's revised reply and finalize using the revised content.
Reject: Record the rejection and reason, and do not mark the rejected draft as resolved. Set an appropriate status such as REJECTED or NEEDS_FOLLOW_UP.
The rejection behavior must be documented. It must not silently mark the ticket as successfully resolved.
Use LangGraph's supported PostgreSQL checkpointer and interrupt/resume mechanism. Persist application-level ticket status separately from graph checkpoints.
Ensure that duplicate review requests cannot finalize the same ticket twice.

9. REST API requirements
Implement documented FastAPI endpoints with Pydantic request and response models.
Suggested routes:
Tickets
POST /api/tickets — validate, create, and start processing a ticket.
GET /api/tickets — list tickets, with useful filtering and pagination.
GET /api/tickets/{ticket_id} — retrieve ticket details and current status.
GET /api/tickets/{ticket_id}/status — retrieve the current stage and status.
GET /api/tickets/{ticket_id}/reply — retrieve the final reply when available.
Human review
GET /api/reviews/pending — list tickets awaiting review.
POST /api/tickets/{ticket_id}/review — submit an approve, edit, or reject decision and resume processing when appropriate.
Use consistent HTTP status codes, clear validation errors, and appropriate not-found/conflict responses.
Return ticket identifiers promptly when processing is asynchronous. Ensure the frontend can poll status without creating duplicate tickets or triggering duplicate LLM calls.
Document the endpoint contracts and provide FastAPI's OpenAPI documentation.

11. Reliability and security
Implement:
Input validation and appropriate request size limits.
Safe error handling for database and LLM failures.
Explicit ticket statuses, including processing, pending review, resolved, rejected/follow-up, and failed states as appropriate.
Clear, actionable error messages without exposing secrets or internal stack traces.
Configurable timeouts and bounded retries for transient failures.
Retry only when safe.
Idempotency for ticket submission and review actions where appropriate.
Protection against duplicate workflow execution and duplicate finalization.
Database transactions for important state transitions.
Logging with ticket IDs and workflow stages, without logging API keys or sensitive information.
